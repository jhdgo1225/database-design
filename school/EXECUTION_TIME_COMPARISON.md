원본 로그: [`school/results/`](results) (`school_before_NN.log`, `school_after_NN.log`, `school_*_meta.txt`). 모든 수치는 이 로그에서 뽑았습니다.

> **이 문서는 학기 비교를 `::CHAR(6)`으로 맞춘 쿼리로 재측정한 결과입니다.** 맞추기 전 첫 측정(17:16) 결과는 아래 '학기 비교 타입 수정 전/후'에 비교용으로 남겼습니다. 첫 측정에서는 2번이 반정규화 후 더 느리게 나왔으나, 원인이 반정규화 구조가 아니라 학기 조건의 추정 오차였습니다.

## 해석할 때 주의할 점

- **메모리는 모든 쿼리에서 작고 디스크를 쓰지 않았습니다.** 모든 해시가 `Batches: 1`이고 `Disk:`가 한 번도 나오지 않았으며, 쿼리별 노드 메모리 합은 34~123 kB로 `work_mem`(4MB)보다 훨씬 작습니다. 메모리 차이는 용량 문제가 아니라 플랜 구조 변화를 보여 주는 지표입니다.
- **실행 노드 메모리가 줄어든 곳은 해시 테이블이 없어진 쿼리입니다.** 3번은 Sort 28 + Hash 12·12·15·10 → Sort 29 + Hash 12·12로 Hash 2개(합 약 25 kB)가 사라졌고, 5번은 Sort 31 + Hash 12·12·11 → Sort 32 + Hash 12·11로 Hash 1개(약 12 kB)가 사라졌습니다. 조인 대상 테이블(강의실·과목)이 없어지면서 그것을 담던 해시 테이블도 없어진 것입니다. 1·2·4번은 노드 구성이 같아 합이 같거나 1 kB 차이입니다.
- **6번은 해시 테이블은 줄었지만 집계 노드가 커졌습니다.** Hash 5개 → 3개로 약 30 kB가 줄었으나 HashAggregate가 32 → 48 kB로 커져 합은 123 → 109 kB(-11%)에 그쳤습니다. 집계 그룹 수는 실제로 둘 다 60개인데 플래너 추정이 전 60, 후 120이라 후에 해시 테이블이 더 크게 잡힌 것으로 보입니다(추정 원인이며 따로 검증하지는 않았습니다). 이 때문에 가장 큰 단일 노드는 전 HashAggregate 32 kB에서 후 HashAggregate 48 kB로 오히려 커졌습니다.
- **정렬(Sort) 메모리는 전/후 25~32 kB로 거의 같습니다.** 정렬하는 행 수가 같기 때문입니다.
- **플래너 메모리 used는 2·3·6번에서 줄었습니다**(231 → 167, 170 → 93, 314 → 257 kB). 조인 수가 줄어 플래너가 다룰 후보가 줄어든 효과로 보이며, 조인 수가 같은 1·4번은 오히려 소폭 늘었습니다(71 → 81, 101 → 111 kB). allocated는 128·256·512 kB 블록 단위라 3번만 256 → 128 kB로 한 단계 내려갔습니다.

- **첫 측정의 결론("3번만 이득, 2번은 후가 느림")은 쿼리 표현 때문에 생긴 것이었습니다.** `CHAR(6)` 학기 컬럼을 `text`와 비교하면 컬럼이 `text(bpchar)` 함수 호출로 변환되어 통계를 쓰지 못하고, 학기 조건 결과를 55행이 아니라 1행으로 추정했습니다. `::CHAR(6)`으로 맞추면 최빈값 통계로 55행을 정확히 추정합니다. 이 때문에 플랜이 전/후 모두 바뀌었습니다.
- **정규화의 3·5번은 강의실 조회 방식이 바뀌었습니다.** 수정 전에는 시간표 55행마다 `tbl_room_l1` 기본키 인덱스를 찾아가(버퍼 165) 실행 버퍼가 181이었습니다. 수정 후에는 강의실 660행을 한 번 읽어 해시 조인하므로(버퍼 4) 20으로 줄었습니다. 그래서 반정규화가 강의실 조인을 없앤 이득은 첫 측정의 181 → 12보다 작은 20 → 12(3번), 20 → 12(5번)입니다.
- **반정규화 2번은 학생으로 먼저 거르는 플랜으로 돌아왔습니다.** 수정 전에는 시간표 55행마다 수강신청을 찾아가 실행 버퍼가 145였고 후가 더 느렸습니다. 수정 후에는 버퍼 33이고 정규화(45)보다 적습니다. 실행 시간은 0.165 → 0.131 ms로 후가 빠릅니다(10회 측정 범위가 겹치지 않음).
- **1번은 조인 수가 같고 후가 약간 느립니다.** 중앙값 0.095 → 0.104 ms(+9%)이지만 10회 측정 범위가 서로 겹쳐서 차이가 있다고 볼 수 없습니다. 합쳐진 `tbl_pers_m2`(60행, 2페이지)를 교수 한 명 조회에 5번 반복해 읽어 버퍼는 8 → 9로 늘었습니다.
- **6번의 개선(중앙값 -23%)이 반복 측정 흔들림보다 큰지는 위 표의 6번 행으로 가늠할 수 있습니다.** 쿼리가 바뀌지 않았는데도 정규화 0.465 → 0.454, 반정규화 0.333 → 0.350 ms로 움직였습니다. 이번 측정에서는 전/후 10회 측정 범위가 겹치지 않지만, 수정 전 측정에서는 범위가 겹쳤던 쿼리라 한 번의 측정으로 확정하지 않는 편이 안전합니다.
- **계획 버퍼·계획 시간은 쿼리마다 증감이 섞입니다.** 조인이 줄어든 쿼리에서 계획 시간이 줄지 않았고 6번의 계획 버퍼는 246 → 321로 늘었습니다. 이 항목은 이번 데이터에서 반정규화의 이득으로 보기 어렵습니다.
- **학번 비교의 타입 차이는 그대로 남아 있습니다.** 전은 `CHAR(10)`(`stud_id = '…'::bpchar`), 후는 `VARCHAR(10)`(`(person_id)::text = '…'::text`)입니다. `VARCHAR → text`는 값을 건드리지 않는 변환이라 통계를 그대로 쓰므로 추정에는 문제가 없었습니다. 별도로, 실험에서 후 쿼리의 학번 비교를 `::char(10)`으로 바꾸면 수정 전 플랜이 뒤집히는 것을 확인했으나 그 메커니즘은 확정하지 못했고 이번 측정에는 반영하지 않았습니다.
- **데이터가 작고 측정은 한 세션입니다.** 모든 쿼리가 0.5 ms 미만이고 전체가 캐시에 올라와 있어, 절대값보다 버퍼·메모리·조인 수 같은 결정적인 지표의 방향을 근거로 삼는 것이 안전합니다. 플랜이 비용 경계에서 갈리는 크기라, 데이터가 커지면 결과가 달라질 수 있습니다.
