# bicycle_rental DB 버전 이력 (패치노트)

PostgreSQL `bicycle_rental` 스키마의 버전별 변경 이력입니다. 스키마가 바뀔 때마다 이 문서 맨 위에 새 버전을 추가합니다.

- 버전 규칙: `MAJOR.MINOR.PATCH`
  - MAJOR: 테이블 추가·삭제, 컬럼 이름·타입 변경 등 기존 쿼리·데이터가 그대로 동작하지 않는 변경
  - MINOR: 기존 쿼리를 깨지 않는 컬럼·제약·인덱스 추가
  - PATCH: 주석·용어·데이터 정정, 샘플·측정 도구 추가 등 구조가 바뀌지 않는 수정
- 기록 시점: 2026-11-14, git HEAD `17cc82b`
- 각 버전은 스키마 파일(DDL), 샘플 데이터, 정보시스템 쿼리 세 가지를 한 묶음으로 봅니다.
- v1.x는 정규화 스키마(`postgresql/`), v2.x는 반정규화 스키마(`postgresql_denormalization/`)입니다. cinema, school, library와 같은 구분입니다.

## v2.0.0: 반정규화 (대여소 이름 복사, 시각 파생 열, 집계 테이블) (현재)

> 커밋: `40139a1` 반정규화 스키마·쿼리·검증 → `4766c2c` 측정 스크립트·로그·비교 문서 → `17cc82b` docker 초기화 경로 (모두 2026-11-14)
> 기준(롤백 지점): v1.2.1 (`106dd27`)
> 구분: MAJOR. 테이블이 4개 늘고 대여 테이블의 구조가 바뀝니다. 다만 정규화 스키마의 열과 제약은 그대로 두고 뒤에 더하는 방식이라, v1.2.1의 INSERT 파일, 날짜 이동, 정규화 쿼리가 이 스키마에서도 그대로 동작합니다.

### 변경 요약

세 가지를 한 버전으로 묶었고, 쿼리는 어느 것을 쓰느냐에 따라 세 벌로 나눠 둡니다.

| 후보 | 내용 | 쓰는 쿼리 |
|---|---|---|
| 2 | 대여 테이블에 대여소 이름을 복사해서 대여소 조인을 없앰 | 1, 4, 5, 7 |
| 3 | 대여 테이블에 대여·반납 년월, 요일, 시간대를 생성 컬럼으로 두어 계산을 없앰 | 1, 2, 4, 5, 7 |
| 1 | 대여 33만 건을 훑지 않도록 집계 테이블 4개를 만들고 트리거로 맞춤 | 1, 2, 4, 5, 6, 7 |

- 후보 1·2·3을 합친 쿼리(`postgresql_information_system.sql`)는 집계 테이블에 복사해 둔 대여소 이름을 읽어서 조인도 없습니다. 이름은 대여 행의 `rtpl_space`, `retrtpl_space`에서 가져오므로 후보 2·3의 열이 후보 1의 집계 테이블을 채우는 구조입니다.
- 후보 1만 쓰는 쿼리(`..._summary.sql`)는 집계 테이블을 읽고 대여소 이름을 `tblrtplM1`과 조인합니다. 후보 2·3만 쓰는 쿼리(`..._row.sql`)는 집계 테이블을 읽지 않습니다. 세 벌을 따로 둔 것은 후보마다 기여를 나눠서 재기 위해서입니다.
- 쿼리 3(파손/분실)은 4천 건짜리 테이블이라 바꾸지 않았습니다.
- `time`, `totalrental` 같은 기존 반정규화는 그대로입니다.

### 스키마 변경

| 대상 | 변경 | 분류 |
|---|---|---|
| `tblrtplM1` | `UNIQUE (rtpl_id, space)` 추가. 아래 복합 FK들의 대상 키 | 제약 추가 |
| `tblrentT1` | `rtpl_space VARCHAR(128) NOT NULL`, `retrtpl_space VARCHAR(128)` 추가. 대여소 이름 복사 | 컬럼 추가 |
| `tblrentT1` | `rtpl_id`, `retrtpl_id`의 단일 FK를 복합 FK `(rtpl_id, rtpl_space)`, `(retrtpl_id, retrtpl_space)` → `tblrtplM1(rtpl_id, space)`(`ON UPDATE CASCADE`)로 바꿈. 이름이 대여소 테이블과 같음을 보장하고, 대여소 이름을 바꾸면 대여 행에 전파됨 | 제약 변경 |
| `tblrentT1` | `CHECK ((retrtpl_id IS NULL) = (retrtpl_space IS NULL))` 추가 | 제약 추가 |
| `tblrentT1` | 생성 컬럼 `rent_ym`(대여한 달의 1일), `rent_dow`(0=일 ~ 6=토), `rent_slot`(1=심야 0~4시, 2=오전 5~11시, 3=오후 12~17시, 4=야간), `return_ym`(반납한 달의 1일, 미반납이면 NULL) 추가 | 컬럼 추가 |
| 집계 테이블 4개 | 아래 "집계 테이블" | 테이블 추가 |
| 트리거·함수 | 아래 "트리거와 함수" | 추가 |

반정규화 열은 모두 `tblrentT1`의 맨 뒤에 붙였습니다. 직접 넣은 값은 이름 열이면 트리거가 덮어쓰고, 생성 컬럼이면 넣을 수 없습니다.

`TO_CHAR(timestamp, text)`는 STABLE이라 생성 컬럼에 쓸 수 없어서(`generation expression is not immutable` 오류를 PostgreSQL 17에서 확인) IMMUTABLE인 `DATE_TRUNC`와 `EXTRACT`를 썼습니다. 쿼리는 `TO_CHAR(rent_ym, 'YYYY-MM')`으로 출력만 바꿉니다.

### 집계 테이블

대여(`tblrentT1`)에서 계산되는 값이라 직접 고치지 않습니다. 개수가 0이 되면 행을 지웁니다.

| 테이블 | 키 | 값 | 쓰는 쿼리 |
|---|---|---|---|
| `tblrpmoS1` 대여소×월 | `(rtpl_id, ym)` | `space`(대여소 이름), `rent_cnt`(대여 대여소, 대여한 달 기준 건수), `ret_cnt`·`ret_fee`(반납 대여소, 반납한 달 기준 건수와 요금 합) | 1, 4 |
| `tblbcmoS1` 자전거×월 | `(bycl_id, ym)` | `rent_cnt`, `time_sum` | 2 |
| `tblrpwdS1` 대여소×요일×시간대 | `(rtpl_id, dow, slot)` | `space`(대여소 이름), `rent_cnt`, `time_sum` | 5, 7 |
| `tblmbrgS1` 회원×구 | `(mebr_id, region)` | `use_cnt`, `time_sum`, `dist_sum`, `carbon_sum` | 6 |

- `tblrpmoS1`, `tblrpwdS1`의 `space`는 대여 행의 `rtpl_space`, `retrtpl_space`를 그대로 가져옵니다. 대여 행과 같은 복합 FK `(rtpl_id, space)`(`ON UPDATE CASCADE`)가 있어서 대여소 이름을 바꾸면 집계 테이블에도 전파됩니다. 이름이 같은 대여소는 정규화 쿼리처럼 한 줄로 합쳐집니다.
- 반납 쪽 집계(`ret_cnt`, `ret_fee`)는 반납 대여소와 반납일시가 둘 다 있는 대여만 셉니다. 쿼리 4가 그렇게 센다는 전제이고, 검증 3번이 두 값이 함께 NULL인지 확인합니다.
- 회원×구는 대여한 대여소의 구와 반납한 대여소의 구에서 한 번씩 셉니다. 구 번호는 대여소 ID의 앞 2자리이고, 같은 구에서 빌려 반납하면 한 행에 2번 더해집니다. 쿼리 6의 `UNION ALL`과 같은 계산입니다.
- 대여 테이블에 이미 외래키가 있어서 `tblbcmoS1`, `tblmbrgS1`에는 외래키를 두지 않았습니다.

### 트리거와 함수

| 이름 | 동작 |
|---|---|
| `trg_rent_fill` (`fn_rent_fill`) | 대여 INSERT와 `rtpl_id`·`retrtpl_id` UPDATE 때 `tblrtplM1.space`에서 이름을 채움. 없는 대여소면 FK 위반 오류. 대여소 이름 변경이 `ON UPDATE CASCADE`로 전파될 때도 돌지만 새 이름을 다시 읽을 뿐이라 같은 값이 됨 |
| `trg_rent_summary` (`fn_rent_summary`, `fn_rent_summary_apply`) | 대여 INSERT/UPDATE/DELETE 때 집계 테이블 4개를 고침. UPDATE는 이전 값을 빼고 새 값을 더하고, 집계에 쓰는 값이 그대로면 건너뜀. 더할 때 행이 없으면 만들고(`space`는 대여 행의 이름 열에서 가져옴), 뺄 때 0이 되면 지움 |
| `fn_rebuild_rent_summary()` | 집계 테이블 4개를 대여 테이블에서 처음부터 다시 만듦 (`TRUNCATE` 후 `INSERT ... SELECT`) |

### 적재 순서

DDL → 기존 샘플 → 날짜 이동 → `ALTER TABLE tblrentT1 DISABLE TRIGGER trg_rent_summary` → 대량 샘플 → `SELECT fn_rebuild_rent_summary()` → `ALTER TABLE tblrentT1 ENABLE TRIGGER trg_rent_summary` → `VACUUM (ANALYZE)` → 검증. 측정 스크립트의 `setup`이 이 순서로 하고 검증에 위반이 있으면 멈춥니다.

대량 샘플 33만 건을 행마다 트리거로 집계하면 느려서, 대량 적재 때는 집계 트리거만 끄고 마지막에 한 번에 만듭니다(재생성은 2초 안팎). 이름을 채우는 `trg_rent_fill`은 끄지 않습니다. 이름이 비면 NOT NULL에 걸립니다.

| 5 | `rtpl_space`, `rent_dow`, `rent_slot`으로 묶고, 요일·시간대 글자는 묶은 뒤 CASE로 만듦 | `tblrpwdS1`을 대여소와 조인해서 묶음 | `tblrpwdS1`의 `space`로 묶음, 조인 없음 |

세 벌 모두 정규화 쿼리(`postgresql/postgresql_information_system.sql`)와 결과가 같아야 합니다. 반정규화 스키마는 정규화의 열을 그대로 가지고 있어서 한 DB에서 네 벌을 모두 실행해 비교합니다.

### 성능 측정 결과 (정보시스템 쿼리 1~7, 대량 샘플)

두 DB에서 쿼리 세트 네 벌을 쿼리마다 순서를 돌려 가며 측정했습니다. 환경, 집계 기준, 쿼리·phase별 표, 병렬 결과, 해석할 때 주의할 점은 [EXECUTION_TIME_COMPARISON.md](EXECUTION_TIME_COMPARISON.md)에 있습니다. 아래는 측정 스크립트를 실행했을 때 대략 이런 집계 결과가 나왔다는 기록이고, 로그 파일은 저장소에 두지 않았습니다. 직렬(`PARALLEL=0`)과 병렬(`PARALLEL=2`)로 스크립트를 실행하면 `results_bulk_interleaved_parallel0/`, `results_bulk_interleaved_parallel2/`에 로그가 생기므로 그 로그로 확인합니다. 시간은 쿼리당 30회의 중앙값, 버퍼·메모리는 3회 중앙값입니다.

- 후보 1·2·3을 합친 쿼리는 정규화보다 직렬에서 91.7%, 병렬에서 89.5% 줄었습니다. 후보 1 단독과의 실행 시간 차이는 +0.7%(직렬), +0.2%(병렬)로 거의 없고, 합친 쪽의 이점은 조인이 없어져서 줄어든 계획 시간·계획 버퍼·계획 메모리(후보 1 대비 -33%, -28%, -25%)에 있습니다.

### 알려진 한계

- 같은 집계 행을 동시에 고치는 대여는 서로 기다립니다. 인기 있는 대여소의 같은 달 행이 가장 붐빕니다. 동시 쓰기 부하는 재지 않았습니다.
- 날짜 이동처럼 대여 33만 건을 한꺼번에 UPDATE하는 작업은 트리거를 끄고 `fn_rebuild_rent_summary()`로 다시 만드는 편이 낫습니다. 이 방식을 실제 33만 건 UPDATE로 재 보지는 않았습니다.
- 대여소 이름을 바꾸면 해당 대여소의 대여 행 전체와 집계 테이블 행이 UPDATE됩니다. 대량 샘플에서 시간은 재지 않았습니다(작은 범위의 정합성만 롤백 트랜잭션에서 확인).
- 집계 테이블 4개는 직접 INSERT/UPDATE/DELETE할 수 있고, 권한이나 트리거로 막지 않았습니다. 직접 고치면 대여 테이블과 값이 어긋나서 쿼리 1·2·4~7이 틀린 값을 냅니다. 어긋났는지는 `postgresql_verify_denormalization.sql`의 6~10번이 찾고, `fn_rebuild_rent_summary()`로 대여 테이블에서 다시 만듭니다. 6번과 7번은 값을 일부러 어긋나게 해서 검출과 재생성을 확인했고, 8·9·10번은 확인하지 않았습니다.
- 쿼리 시간은 한 번의 실험이고 호스트 상태에 따른 실험 간 차이는 확인하지 않았습니다. `work_mem` 조정과 정렬 쿼리 튜닝은 이 비교를 마쳤으므로 이제 진행할 수 있습니다.
- MySQL은 만들지 않았습니다.

### 호환성에 미치는 영향

- 대여 INSERT는 v1.2.1과 같은 열 목록으로 그대로 됩니다. 이름 열은 트리거가 채우고 파생 열은 생성 컬럼입니다.
- 존재하지 않는 대여소를 넣으면 이전의 FK 위반 대신 `trg_rent_fill`이 같은 오류 코드(`foreign_key_violation`)로 거부합니다.
- 대여가 INSERT/UPDATE/DELETE될 때마다 집계 테이블이 같이 바뀌어서 쓰기가 느려집니다(위 측정).
- `tblrentT1`의 `SELECT *`는 열이 6개 늘어납니다.

기존 샘플이 아래 규칙과 맞지 않는 곳을 고쳤습니다. 규모는 v1.0.0과 같고, 보충/수거만 20건에서 25건으로 늘었습니다.

| 규칙 | 내용 |
|---|---|
| 자전거 상태 | ING는 거치대에 없고 미반납 대여가 있는 자전거. 거치대에 들어오면 AVL이 되고 대여 이력(반납 대여소, 반납일시)도 같이 갱신. 미반납 대여의 자전거는 ING 또는 LST |
| 분실 | 청구까지 확정된 분실(`liable` Y, `confirm` Y) 4건은 미반납 대여 + LST 자전거와 연결. 나머지 분실 신고는 이후 회수된 것으로 보고 반납 완료 대여에 연결. 파손/분실 20건은 모두 `rent_id`로 대여와 연결 |
| 속도 | 15분 이하 대여는 평균 시속 36km, 그보다 길면 25km 이내. 넘으면 상한의 0.9배로 `dist`, `kcal`, `carbon`을 비례해서 줄임 |
| 대여 연속성 | 같은 자전거의 다음 대여 시작 대여소 = 이전 반납 대여소. 사이에 보충(SP)이 있으면 그 보충 대여소. 수거(CL) 뒤 대여는 보충을 거쳐야 하고, 수거 대여소 = 직전 위치. 마지막 이벤트가 CL이면 거치 해제, 상태가 COL이면 마지막 이벤트가 CL. 반납한 자전거가 거치대에 없어도 허용하고, 거치돼 있으면 거치대 대여소 = 마지막 위치 |
| 요금 | 이 시점에는 2건 수정 (정책은 v1.2.0에서 다시 바뀜) |

`f35890f`에서 대여 50건 중 바뀐 값은 반납 대여소 18건, 시작 대여소 25건, 자전거 8건, 반납일시 5건, 거리·칼로리·탄소 5건, 요금 2건, 회원 1건입니다. 마지막 이벤트가 보충(SP)인 자전거는 거치대를 그 대여소로 옮겼고, `b270f74`에서 GN00014와 SD00026을 마지막 이벤트(SP)에 맞춰 AVL로 바꿨습니다 (SD00026은 04001 대여소의 SD 거치대 0400102를 AVL로 바꿔서 거치). MySQL 샘플(`d89d4a4`)은 같은 내용입니다.

### 검증

이 버전을 만들 때는 검증 스크립트 없이 직접 확인했습니다. 지금은 v1.2.1의 `postgresql_verify_data.sql` 34개 규칙 중 자전거 상태·거치대(7~10번), 대여 연속성(11~16번), 파손/분실(20~25번), 수거 사유(26번)로 현재 샘플을 확인할 수 있고 위반은 0건입니다.

### 특징

- 코드값은 `CHECK`로 제한합니다 (자전거 상태 `PD/AVL/ING/DMG/LST/RP/COL`, 구분 `GN/SD`, 이용권 코드와 결제수단의 형식 등).
- `tblrentT1.time`(`INTERVAL`)과 `tblmebrM1.totalrental`은 계산을 피하려고 둔 반정규화입니다.
- `dist`, `kcal`, `carbon`은 `REAL`이고, 파손/분실은 대여와 연결되지 않으며, 인덱스는 기본키 외에 없습니다.
- 정보시스템 쿼리 7개와 테이블 조회 쿼리를 함께 둡니다. 샘플 날짜는 2025-04 ~ 2025-05입니다.
