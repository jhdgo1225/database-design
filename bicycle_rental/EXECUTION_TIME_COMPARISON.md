# 자전거 대여 정보시스템 쿼리 응답시간·리소스 비교 (정규화와 반정규화 v2.0.0, 대량 샘플)

측정 스크립트(`estimation_response_time_and_resource.sh`)를 실행했을 때 대략 이런 집계 결과가 나왔다는 기록입니다. 로그 파일은 저장소에 두지 않았습니다. 직렬(`PARALLEL=0`), 병렬(`PARALLEL=2`)로 스크립트를 실행하면 `results_bulk_interleaved_parallel0/`, `results_bulk_interleaved_parallel2/`에 `bicycle_<phase>_NN.log`(자원 측정), `bicycle_<phase>_NN_time.log`(시간 측정), `bicycle_before_meta.txt`, `bicycle_after_meta.txt`가 생기고, 이 로그를 `summarize_estimation_result.sh`로 요약해서 확인합니다. phase는 `before`(정규화), `a23`(후보 2·3), `a1`(후보 1), `a123`(후보 1·2·3을 합친 것)입니다. 표의 수치는 한 번 실행한 로그에서 뽑았고, 로그에 없는 값은 따로 적었습니다. 다시 실행하면 시간은 조금씩 달라집니다.

> **로그 파일 안내:** 이 문서가 말하는 측정 로그(`bicycle_<phase>_NN.log`, `bicycle_<phase>_NN_time.log`, `bicycle_*_meta.txt`, v1.2.1 시점의 `bicycle_NN.log`)는 저장소에 없습니다. 로그를 열어 보려면 반드시 측정 스크립트(`bicycle_rental/estimation_response_time_and_resource.sh`)를 실행해서 생성해야 합니다. 이 문서의 수치를 확인하려고 새로 측정하면 값이 조금 다를 수 있습니다. 시간은 호스트 상태에 따라 달라지고, 캐시 상태에 따라 달라지는 값(버퍼 read 등)도 있습니다. 대량 샘플은 `CURRENT_DATE` 기준으로 만들어져서 실행한 날짜에 따라 행 수도 조금 달라집니다.

v1.2.1에서 정규화만 잰 기준값(`results_parallel0/`, `results_parallel2/`, 이후 저장소에서 삭제)은 DB 하나에서 날짜가 다른 데이터로 잰 것이라 이 문서의 수치와 직접 비교하지 않습니다.

- 쓰기는 크게 느려졌습니다. 반납 완료 대여를 2만 건 복사해 넣는 INSERT가 542 ~ 581 ms에서 3.2 ~ 5.0 s로, 2만 건 UPDATE가 410 ~ 424 ms에서 12.2 ~ 14.9 s로 늘었습니다(로그 밖 값, 아래 "쓰기 비용").
- 데이터는 합성이고 Docker 안의 한 호스트에서 측정했으므로 운영 성능을 예측하는 근거로 쓰기는 어렵습니다.

## 측정 기준

| 항목 | 내용 |
|---|---|
| 실행 환경 | 실제 컨테이너 `db-optimization-postgres`, PostgreSQL 17.10 (aarch64), `shared_buffers`=16384 페이지(128MB), `work_mem`=4MB, `jit`=on, TimeZone=UTC, `max_parallel_workers_per_gather` 직렬 0 / 병렬 2 |
| DB | `bicycle_rental_normalized_bench`(정규화), `bicycle_rental_denormalized_bench`(반정규화) 두 개를 따로 만들어 둠. 같은 인스턴스라 `shared_buffers`를 함께 씀. 실제 `bicycle_rental` DB는 건드리지 않음 |
| 스키마 | 정규화: `postgresql/`(v1.2.1). 반정규화: `postgresql_denormalization/`(v2.0.0) |
| 통계 상태 | 적재 직후 `default_statistics_target = 2000`으로 `VACUUM (ANALYZE)`. 표본(60만 행)이 가장 큰 테이블(대여 33만 행)보다 커서 전체 행을 읽으므로 같은 데이터에서는 같은 통계가 나옴 |
| 데이터 | 기본 샘플 + 날짜 이동 + 대량 샘플. 두 DB 모두 대여 332,705건(2025-11-14 ~ 2026-11-13), 회원 20,030, 자전거 2,530, 대여소 420. 반정규화 DB는 대량 샘플 전에 집계 트리거를 끄고 적재 뒤 집계 테이블을 다시 만든 다음, `postgresql_verify_denormalization.sql` 10개가 모두 0인 것을 확인하고 측정함. 집계 테이블 행 수는 `tblrpmoS1` 5,220, `tblbcmoS1` 29,318, `tblrpwdS1` 10,995, `tblmbrgS1` 282,134 |
| 쿼리 | 정규화: `postgresql/postgresql_information_system.sql`. 후보 2·3: `..._row.sql`, 후보 1: `..._summary.sql`, 후보 1·2·3: `postgresql_denormalization/postgresql_information_system.sql`. 줄 끝 주석을 제거하고 `;` 단위로 분리해 그대로 실행. 측정 전에 `verify_query_equivalence.sh`로 네 가지의 출력이 모두 같은 것을 확인함 |
| 자원 측정 | `EXPLAIN (ANALYZE, BUFFERS, MEMORY, WAL, SETTINGS, SUMMARY)`를 쿼리마다 모든 phase에 워밍업 3회(버림) 후 3회. 버퍼·메모리·플랜·결과 행수를 읽는 용도 |
| 시간 측정 | `EXPLAIN (ANALYZE, TIMING OFF, BUFFERS OFF, MEMORY OFF, SUMMARY ON)`을 쿼리마다 모든 phase에 워밍업 3회(버림) 후 30회. 실행 시간과 계획 시간을 읽는 용도 |
| 실행 순서 | 두 측정 모두 한 회마다 phase 순서를 한 칸씩 돌림(1회: 정규화, 후보 2·3, 후보 1, 합친 것 / 2회: 후보 2·3, 후보 1, 합친 것, 정규화 ...). 쿼리마다 자원 측정 뒤에 시간 측정. 캐시 초기화는 하지 않음 |
| 측정 시각 | 직렬 2026-11-14 19:50 (KST) 시작, 병렬 19:58 시작. `current_date=2026-11-14` |
| 실행 명령 | `sh bicycle_rental/estimation_response_time_and_resource.sh setup` 후 `PARALLEL=0 ... measure`(직렬), `PARALLEL=2 ... measure`(병렬) |

## 집계 기준

| 지표 | 로그에서 읽는 값 | 집계 |
|---|---|---|
| 실행 시간 | 시간 로그의 `Execution Time` | 30회의 중앙값. 사분위 범위(1~3사분위)와 변동계수(CV)는 보조 |
| 계획 시간 | 시간 로그의 `Planning Time` | 30회의 중앙값 |
| 실행 버퍼 | 자원 로그 플랜 최상위 노드의 `Buffers: shared hit` + `read`(병렬 워커 포함, `temp` 제외). `read`는 따로도 표시 | 3회 중앙값 |
| 계획 버퍼 | 자원 로그 `Planning:` 블록의 `Buffers: shared hit` | 3회 중앙값 |
| 계획 메모리 | 자원 로그의 `Memory: used=…kB` | 3회 중앙값 |
| 실행 노드 메모리 | 각 노드의 `Sort Method … Memory`, `Memory Usage`(Hash, HashAggregate)와 Incremental Sort의 Peak Memory | 노드별 값을 합산(근사치이며 동시 점유량이 아님). 디스크로 내려간 양(`Disk:`)은 포함하지 않고 따로 표시 |
| 디스크 | 정렬의 `Disk:`, 집계의 `Disk Usage` | 3회 중앙값, 병렬이면 워커 몫 포함 |
| 변화율 | (해당 phase − 정규화) ÷ 정규화 | 합계 행은 쿼리별 중앙값의 합 |
| 판정 | 후보 1과 합친 것의 30회 사분위 범위가 겹치면 "겹침". 변화가 3% 안쪽이면 범위가 겹치지 않아도 "3% 이내"로 두고 차이로 보지 않음 | |

## 해석할 때 주의할 점

- **후보 2·3의 큰 감소는 플랜이 바뀐 덕입니다.** 정규화 쿼리 1은 `TO_CHAR(...)` 식으로 묶어서 33만 행을 디스크에서 정렬(13 MB)한 뒤 GroupAggregate를 합니다(계측 옵션을 켠 첫 실행에서 전체 750 ms 중 조인 끝이 137.6 ms, 정렬 끝이 721.4 ms라 정렬이 약 584 ms로 가장 큽니다). 후보 2·3은 일반 열로 묶어서 그룹 수(약 5천)를 보고 HashAggregate를 고릅니다. 쿼리 4·5·7도 같은 모양이고 디스크 사용이 0이 되었습니다. 정규화 쿼리 2는 `bycl_id` 인덱스 순서로 읽는 Incremental Sort 위의 GroupAggregate(버퍼 332,727)였는데 후보 2·3에서 순차 스캔 + HashAggregate(7,745)로 바뀌었습니다.
- **후보 2·3은 읽는 페이지가 늘었습니다.** 대여 테이블이 43 MB에서 61 MB로 커져서 순차 스캔하는 쿼리 1·4·5·6·7의 버퍼(hit + read)가 직렬에서 약 42% 늘었습니다(예: 5,464 → 7,742, 병렬은 38 ~ 42%). 대여 테이블의 순차 스캔이 5,455 페이지에서 7,739 페이지로 늘었습니다(쿼리 1의 순차 스캔 노드의 버퍼, 로그 `bicycle_before_01.log`, `bicycle_a23_01.log`). 그래도 정렬이 사라진 이득이 더 커서 시간은 크게 줄었습니다.
- **집계 테이블을 읽는 쿼리 1·4·5는 버퍼가 52 ~ 126블록으로 줄었습니다.** 쿼리 6은 반대로 283,362블록입니다. `tblmbrgS1`을 기본키 순서로 인덱스 스캔하면서 행(28만 개)마다 버퍼에 한 번씩 접근한 횟수이고, 서로 다른 페이지 수는 아닙니다(이 테이블은 인덱스를 포함해 약 34 MB, 약 4천 페이지). 시간은 1,431 ms에서 264 ms로 줄었으므로 버퍼 합계로 쿼리를 비교하기 어렵습니다. 합계 행의 -20%는 정규화 쿼리 2(332,727블록)와 집계 테이블 쿼리 6(283,362블록)이 합계 대부분을 차지해서 나온 값이라 의미가 작습니다.
- **합친 쿼리 5가 후보 1보다 느린 이유(확정하지는 않음):** 후보 1의 플랜은 조인 뒤 정렬하고 GroupAggregate를 하고, 합친 쿼리는 집계 테이블을 HashAggregate로 묶은 뒤 정렬합니다. 합친 쿼리의 플랜은 그룹 수를 1,100개로 추정했는데 실제는 10,995개였습니다. 차이는 약 1.6 ~ 1.8 ms(직렬 +5.6%, 병렬 +5.3%)로 작지만 두 번의 측정 모두 범위가 분리되었습니다. 원인이 추정 오차 때문인지는 확인하지 않았습니다.
- **합친 것의 이점이 작은 이유:** 후보 1의 쿼리가 조인하던 `tblrtplM1`이 420행뿐이라 실행 비용이 작습니다(후보 1의 쿼리 5 플랜에서 대여소 조인 노드는 하위 스캔을 포함해 약 2.6 ~ 2.7 ms, 3회 모두, 계측 옵션을 켠 실행 기준). 조인을 없애면 계획 시간·계획 버퍼·계획 메모리가 줄지만 실행 시간은 거의 달라지지 않습니다.
- **노드 메모리가 늘어난 것은 메모리를 더 쓴다는 뜻이 아닙니다.** 정규화는 외부 병합 정렬(디스크)이라 노드 메모리에 정렬 몫이 들어가지 않고 디스크로 따로 잡힙니다(138,144 kB). 후보 2·3 이후로는 HashAggregate가 메모리에 들어가서 노드 메모리가 늘고 디스크는 줄었습니다. 쿼리 6의 후보 2·3은 정렬(18,336 kB)과 해시 집계(46,192 kB)가 여전히 `work_mem`(4MB)을 넘어 디스크를 씁니다(합 64,528 kB).
- **`shared read`:** 정규화 쿼리 1은 대여 테이블 5,455페이지 중 5,262 / 5,230 / 5,198페이지를 `shared_buffers`에서 찾지 못하고 읽었습니다(자원 측정 3회). 회마다 정확히 32페이지(256 KB)씩 줄었는데, 큰 테이블의 순차 스캔이 쓰는 링 버퍼(`shared_buffers`의 1/4 = 4,096페이지보다 큰 테이블)의 크기와 같습니다. 그러나 후보 2·3의 쿼리 1은 더 큰 테이블(7,739 페이지)을 읽는데도 `read`가 0이고, 후보 2·3은 쿼리 2·4·5·6·7에서 127 ~ 5,306페이지를 읽습니다. 링 버퍼만으로는 설명되지 않고, 두 DB(합쳐 208 MB)가 `shared_buffers` 128 MB를 같이 쓰는 상태에서 앞선 쿼리가 무엇을 남겼는지에도 달라졌을 것으로 보이지만 확인하지는 않았습니다. 그래서 버퍼는 hit만이 아니라 hit + read로 비교했습니다.
- **쓰기 비용:** 위 읽기 측정은 집계 트리거 비용을 포함하지 않습니다. 아래 "쓰기 비용"을 같이 보세요.

### 쓰기 비용 (로그 밖, 롤백 트랜잭션에서 3회)

반납 완료 대여 2만 건을 복사해 넣거나(INSERT) `returndate`, `fee`를 고치는(UPDATE) 문장을 `EXPLAIN (ANALYZE, TIMING OFF)`로 재고 롤백했습니다. 서버 병렬은 0입니다. 반정규화는 트리거를 켠 상태입니다.

| 작업 (2만 건) | 정규화 | 반정규화 |
|---|---|---|
| INSERT | 542 ~ 581 ms | 3.2 ~ 5.0 s (1, 2, 3회가 3.2, 4.0, 5.0 s로 점점 늘어남) |
| UPDATE | 410 ~ 424 ms | 12.2 ~ 14.9 s |

반정규화의 INSERT가 회를 거듭하며 느려진 이유는 확인하지 않았습니다. 롤백한 같은 집계 행 UPDATE가 쌓여서 죽은 튜플이 늘었을 수 있고, 이 쓰기 측정은 읽기 측정 뒤에 같은 DB에서 했습니다. 측정 뒤 반정규화 DB의 대여 테이블과 `tblmbrgS1`은 위 측정 때보다 커져 있으므로(대여 테이블 7,739 → 10,986 페이지, `tblmbrgS1` 34 MB → 64 MB) 읽기 측정을 다시 하려면 `REBUILD=1`로 DB를 새로 만드세요. 같은 집계 행을 동시에 고치는 쓰기가 서로 기다리는 영향은 재지 않았습니다.

## 한계

- 한 번의 실험입니다. 사분위 범위와 CV는 이 실험 안의 변동만 보여 주고, 호스트 상태가 달라질 때 생기는 실험 간 차이는 반영하지 않습니다. 직렬과 병렬은 같은 DB를 연달아 측정한 것이라 독립된 반복이 아니므로, 절대값보다 방향이 같은지를 근거로 삼는 것이 안전합니다.
- 후보 1과 합친 것의 쿼리 1·4·7은 차이가 -1 ~ -4%라 이번 측정만으로 방향을 단정하기 어렵습니다.
- 워커가 없는 쿼리도 직렬 측정과 병렬 측정 사이에 최대 약 -11%(쿼리 2, 6)가 달라졌습니다. 쿼리 3처럼 모든 phase가 같은 쿼리도 직렬에서 병렬로 가며 -4 ~ -6% 줄었습니다. 두 측정은 같은 DB에서 시간을 두고 한 것이라 이 정도의 실험 간 변동이 있고, 병렬 합과 직렬 합의 차이를 병렬 효과로만 읽을 수 없습니다.
- 시간은 서버가 보고하는 `Execution Time`이고 결과 전송 시간은 들어 있지 않습니다. 쿼리 6은 28만 행이라 클라이언트가 받는 시간이 더 걸릴 수 있습니다.
- 자원 측정은 쿼리·phase마다 3회입니다. 노드별 실행 시간은 계측 비용이 섞여 있어 원인 분석에 쓰지 않았습니다.
- 두 DB가 `shared_buffers`를 함께 씁니다. `shared_buffers`나 `work_mem`을 바꿔 다시 측정하지 않았습니다. `work_mem` 조정과 정렬 쿼리 튜닝은 이 비교를 마친 뒤로 미룬 작업입니다.
- 데이터는 합성입니다. 한 호스트의 Docker 컨테이너에서 측정했습니다.
