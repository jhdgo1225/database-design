# 영화관 정보시스템 쿼리 응답시간·리소스 비교 (반정규화 전/후)

원본 로그: [`cinema/results/`](results) (`cinema_before_NN.log`, `cinema_after_NN.log`, `cinema_*_meta.txt`). 모든 수치는 이 로그에서 뽑았습니다.

## 결론

| 구분 | 결과 (9개 쿼리 합, 중앙값, 전 → 후) |
|---|---|
| 실행 시간 | 7.29 → 7.13 ms (-2%). **어느 쿼리도 전/후 10회 분포가 겹쳐서 차이가 있다고 볼 수 없습니다.** |

## 측정 기준

| 항목 | 내용 |
|---|---|
| 실행 환경 | 실제 컨테이너 `db-optimization-postgres`, PostgreSQL 17.10 (aarch64), `shared_buffers`=16384 페이지(128MB), `work_mem`=4MB, `jit`=on, `max_parallel_workers_per_gather`=2, TimeZone=UTC |
| DB | `cinema_bench` 한 DB. **전 스키마·데이터 적재 → 측정 → `public` 스키마 삭제 → 후 스키마·데이터 적재 → 측정** 순서. 측정용 DB는 끝나면 삭제하므로 실제 `cinema` DB는 건드리지 않음 |
| 전 / 후 스키마 | 전: `cinema/postgresql/` (룩업 테이블 포함 정규화). 후: `cinema/postgresql_denormalization/` |
| 통계 상태 | 적재 직후 **모든 테이블에 전체 `ANALYZE`**. 전/후 모두 모든 테이블이 분석된 상태이며 `cinema_*_meta.txt`에 기록 |
| 데이터 | 전/후 동일한 샘플 데이터(2026-10 기준): 회원 30, 영화 10, 상영관 10, 좌석 1,750, 상영 948, 예매 80, 충전 40 |
| 쿼리 | `cinema/postgresql/postgresql_information_system.sql`(전)과 `cinema/postgresql_denormalization/information_system.sql`(후)의 1~9번. 전체 줄 주석을 제거하고 `;` 단위로 분리해 그대로 실행 |
| 실행 방식 | `EXPLAIN (ANALYZE, BUFFERS, MEMORY, WAL, SETTINGS, SUMMARY)`, 쿼리당 연속 10회. 첫 회를 버리지 않고 캐시 초기화도 하지 않음(전 구간 버퍼 hit) |
| 시간 의존 쿼리 | "이번 달"은 `CURRENT_DATE`, 8·9번은 현재 시각 이후 상영만 대상이라 결과 행수가 날짜·시각에 따라 달라짐. 전(02:37:45)과 후(02:37:53)를 8초 간격으로 측정했고 두 쿼리 모두 76행으로 동일 |
| 실행 명령 | `sh cinema/estimation_response_time_and_resource.sh` |

## 집계 기준

| 지표 | 로그에서 읽는 값 | 집계 |
|---|---|---|
| 실행 시간 | `Execution Time` | 10회의 **중앙값**을 대표값으로 사용. 평균·최소·최대·표준편차는 보조 |
| 계획 시간 | `Planning Time` | 중앙값 |
| 실행 버퍼 | 플랜 최상위 노드의 `Buffers: shared hit` (실행 전체 누적), `read`·`dirtied`·`written` 별도 확인 | 중앙값 |
| 계획 버퍼 | `Planning:` 블록의 `Buffers: shared hit` | 중앙값 |
| 플래너 메모리 | `MEMORY` 옵션의 `Memory: used=…kB allocated=…kB` | 중앙값 |
| 실행 노드 메모리 | 각 노드의 `Sort Method … Memory`, `Memory Usage`(Hash, HashAggregate, Memoize) | 노드별 값을 합산(근사치이며 동시 점유량이 아님), 최대 노드는 별도 표기 |
| 노드 수 / 조인 수 / 스캔 수 | `(cost=…)` 줄 수 / `Hash (Left·Right) Join`, `Nested Loop`, `Merge Join` 노드 수 / `Scan on` 노드 수 | 첫 실행 기준(10회 동일) |
| 결과 행수 | 최상위 노드의 `actual … rows=` | 전/후 동일해야 비교 대상으로 인정 |
| 변화율 | (후 − 전) ÷ 전 | 합계 행은 쿼리별 중앙값의 합 |
| 차이 판정 | **실행 시간**은 전/후 10회의 최소~최대 범위가 겹치면 차이로 보지 않음. 버퍼·메모리·조인 수는 반복해도 거의 같으므로 값 그대로 비교 | |

중앙값을 쓰는 이유는 한 번씩 튀는 값 때문입니다. 예를 들어 2번 후의 최대 0.238 ms, 9번 후의 최대 1.032 ms는 중앙값(0.029, 0.283)과 크게 달라 평균(0.052, 0.360)을 왜곡합니다.

## 해석할 때 주의할 점

- **실행 시간은 노이즈 수준입니다.** 변경이 없는 7번도 +8%(0.071 → 0.076 ms), 3번도 +13%로 나왔습니다. 0.1 ms 안팎의 차이는 반복 측정의 흔들림으로 봐야 하며, 4·8번의 -7~8%도 같은 범위입니다.
- **5번은 시간의 대부분이 정렬입니다.** 약 5 ms 중 약 4.8 ms가 948행을 제목·상영일로 정렬하는 `Sort` 단계이고, 제거된 조인의 비용(0.1~0.2 ms)은 그에 비해 작습니다.
- **실행 버퍼가 줄지 않은 이유**: 정규화 구조의 4번 플랜은 `tbl_thtr_m1`을 `Seq Scan` + 해시 조인으로 1버퍼만 읽으므로, 조인을 없애도 아낄 버퍼가 거의 없습니다. 반면 컬럼이 추가되어 테이블이 커졌습니다(`tbl_scrn_m1` 8→9페이지, `tbl_bytk_d1` 1→2페이지). 조인과 무관한 3·6번의 버퍼가 +1씩 늘어난 것도 같은 이유입니다.
- **통계 상태에 따라 결과가 달라질 수 있습니다.** 이 측정은 모든 테이블에 통계가 있는 조건(`ANALYZE` 후)에서만 했습니다. 통계가 없으면 옵티마이저가 다른 조인 방식을 고를 수 있어 특히 버퍼 수가 달라질 수 있으며, 이 문서에서는 측정하지 않았습니다.
- **실행 노드 메모리는 거의 같습니다.** 8번만 늘었는데(48 → 73 kB) 스키마가 아니라 집계 방식이 `GroupAggregate`에서 `HashAggregate`로 바뀐 플랜 변화입니다.
- **6번은 비교 기준이 바뀌었습니다.** `buydate`(결제 완료 시각)가 아니라 `reserved_at`(예약 시도 시각)을 사용합니다. 결과는 같았습니다(3행).
- **데이터가 작고 측정은 한 세션입니다.** 절대값보다 버퍼·메모리·조인 수 같은 결정적인 지표의 방향을 근거로 삼는 것이 안전합니다.
