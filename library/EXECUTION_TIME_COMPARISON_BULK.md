# 도서관 정보시스템 쿼리 응답시간·리소스 비교 (반정규화 전/후, 대량 샘플, 직렬·병렬 구분)

측정 스크립트(`library/estimation_response_time_and_resource.sh`)를 실행했을 때 대략 이런 집계 결과가 나왔다는 기록입니다. 로그 파일은 실행 방식별로 폴더가 나뉘어 생성되고, 모든 수치는 한 번 실행한 이 로그에서 뽑았습니다. 로그는 저장소에 두지 않았으므로 직렬(`library/results_parallel0/`)은 스크립트를 `PARALLEL=0`으로, 병렬(`library/results/`)은 `PARALLEL` 없이 실행해서 확인합니다. 다시 실행하면 시간은 조금씩 달라집니다.

> **로그 파일 안내:** 이 문서가 말하는 측정 로그(`library_<before|after>_NN.log`, `library_*_meta.txt`)는 저장소에 없습니다. 로그를 열어 보려면 반드시 측정 스크립트(`library/estimation_response_time_and_resource.sh`)를 실행해서 생성해야 합니다. 이 문서의 수치를 확인하려고 새로 측정하면 값이 조금 다를 수 있습니다. 시간은 호스트 상태에 따라 달라지고, 캐시 상태에 따라 달라지는 값(버퍼 read 등)도 있습니다.

| 구분 | 폴더 | 설정 | 병렬 노드(`Gather`)가 있는 로그 |
|---|---|---|---|
| **직렬 실행** | `library/results_parallel0/` (스크립트 실행 시 생성) | `PARALLEL=0` → `max_parallel_workers_per_gather=0` (병렬을 끔) | 0 / 16 |
| **병렬 실행** | `library/results/` (스크립트 실행 시 생성) | 서버 기본값 `max_parallel_workers_per_gather=2` (플래너가 비용으로 병렬 여부를 선택) | 9 / 16 |

저장 공간·계획 시간 원인 실험과 재현 실험(2차)은 로그가 아니라 별도 임시 DB와 임시 폴더에서 확인한 값이며 해당 절에 표시했습니다.

> **이 문서는 [`EXECUTION_TIME_COMPARISON.md`](EXECUTION_TIME_COMPARISON.md)(DBeaver로 기본 샘플을 측정)를 대체하지 않는 별도 측정입니다.** 조건이 서로 다르므로 두 문서의 수치를 직접 비교하지 마세요.
> 달라진 점: (1) 보유도서 기본키가 `book_held_id`(UUID)에서 **`(book_id, book_no)` 복합 키**로 바뀌었고, (2) 대출 약 18만 건의 **대량 샘플**로 측정하며, (3) `estimation_response_time_and_resource.sh`로 쿼리당 **워밍업 3회 + 측정 30회**를 수행했고, (4) 전/후가 서로 다른 병렬 전략을 고르는 쿼리가 있어 **직렬과 병렬을 구분해** 측정했습니다.

- **직렬 기준으로 반정규화의 이득은 3·6번에만 있습니다.** 3번 4.73 → 2.59 ms(-45%), 6번 82.3 → 59.6 ms(-28%)입니다. 합계로는 -5%입니다.
- **병렬 기준의 -15%는 병렬 실행의 영향이 큽니다.** 1번이 전(직렬)에서 후(병렬)로 바뀌며 83.5 → 45.4 ms(-46%)가 된 것이 합계의 대부분입니다. 같은 직렬끼리 비교한 1번은 -5%이고 범위가 겹칩니다.
- **조인과 무관한 2·4·7·8번(대출 테이블만 읽음)은 후가 같거나 약간 느립니다**(직렬 +1~+12%, 병렬 +0.4~+16%). 실행 버퍼가 +11~+14% 늘었습니다. 반정규화된 `tbl_loan_1`에 연체 이력 컬럼이 들어가 행이 넓어지고 테이블이 2,097 → 2,383 페이지(+14%)로 커졌기 때문입니다. 이 중 4번이 가장 일관되게 느렸습니다.
- **5번은 조인이 줄었는데도 후가 약간 느립니다**(직렬 +8%, 병렬 +7%). 직렬은 범위가 겹치고 병렬은 겹치지 않았습니다. 대출 테이블 전체 읽기가 시간 대부분을 차지하고, 그 테이블이 커진 효과가 조인 제거 이득을 넘어선 것으로 보입니다(추정, 따로 검증하지는 않았습니다).
- **계획 시간은 직렬·병렬 모두 오히려 늘었습니다.** 대출과 보유도서를 `(book_id, book_no)` 두 컬럼으로 조인하는 1·5·6번이 0.9 → 2.3 ms입니다. 원인은 '계획 시간이 늘어난 이유'에서 설명합니다.
- 데이터가 대출 18만 건 규모의 합성 샘플이라, 이 값으로 운영 성능을 예측하기는 어렵습니다.

|---|---|

| 전 / 후 스키마 | 전: `library/postgresql/` (정규화, 도서·보유도서·회원·대출·연체 등 15개 테이블). 후: `library/postgresql_denormalized/` (도서·연체·상태·등급 테이블을 보유도서·회원·대출에 흡수, 보유도서 PK `(book_id, book_no)`, 서지 정보 정합성 트리거 3개, ISBN 검증 CHECK, ISBN EXCLUDE 제약) |

## 집계 기준

| 지표 | 로그에서 읽는 값 | 집계 |
|---|---|---|
| 실행 시간 | `Execution Time` | 30회의 **중앙값**을 대표값으로 사용. 평균·최소·최대·사분위 범위(IQR)·변동계수(CV)는 보조 |
| 계획 시간 | `Planning Time` | 중앙값 |
| 실행 버퍼 | 플랜 최상위 노드의 `Buffers: shared hit` (실행 전체 누적, 병렬 워커 포함), `read`·`dirtied`·`written` 별도 확인 | 중앙값 |
| 계획 버퍼 | `Planning:` 블록의 `Buffers: shared hit` | 중앙값 |
| 플래너 메모리 | `MEMORY` 옵션의 `Memory: used=…kB allocated=…kB`. used는 실제 사용량, allocated는 확보한 블록 크기 | 중앙값 |
| 실행 노드 메모리 | 각 노드의 `Sort Method … Memory`, `Memory Usage`(Hash, HashAggregate). **병렬 워커의 줄(`Worker N:`)은 제외하고 리더 값만 사용** | 노드별 값을 합산(근사치이며 동시 점유량이 아님), 가장 큰 단일 노드는 별도 표기, 중앙값 |
| 노드 수 / 조인 수 | `(cost=…)` 줄 수 / `Hash (Left·Right) Join`, `Nested Loop`, `Merge Join` 노드 수 | 첫 실행 기준 (30회 동일) |
| 결과 행수 | 최상위 노드의 `actual … rows=` | 전/후 동일해야 비교 대상으로 인정 |
| 변화율 | (후 − 전) ÷ 전 | 표에는 ±10% 이상일 때만 표시. 합계 행은 쿼리별 중앙값의 합 |
| 차이 판정 | **실행 시간**은 전/후 각각 30회 중 가장 빠른 값~가장 느린 값(최소~최대)의 범위를 구해 비교한다. 두 범위가 **서로 겹치지 않으면 '차이 있음'**, 조금이라도 **겹치면 '차이 없음'**으로 본다. 30회에는 일시 지연 이상치가 섞여 범위가 넓어지므로 IQR과 CV를 함께 적었다. 버퍼·메모리·조인 수는 반복해도 같으므로 값 그대로 비교 | |

| 연체 `tbl_overdue_1` | 3.09 / 0.83 | (없음, 대출에 흡수) |
| **전체 합 (모든 테이블)** | **23.5 / 5.8 = 29.3** | **22.9 / 5.6 = 28.5 (-3%)** |

- 보유도서가 도서 정보를 사본마다 중복 저장하므로 5,015행짜리 도서 테이블이 사라진 대신 보유도서가 0.94 → 1.80 MB로 커졌습니다. 보유도서 인덱스가 0.39 → 1.33 MB로 커진 것은 ISBN `EXCLUDE` 제약의 GiST 인덱스 때문입니다.
- 쿼리 3(`194 → 228` 버퍼)은 도서(77) + 보유도서(117) 페이지를 읽던 것이 커진 보유도서(228)만 읽는 것으로 바뀐 결과입니다.
- 쿼리 7·8(직렬 `2100 → 2386`, `2097 → 2383`)의 버퍼 증가 286은 대출 테이블이 2,097 → 2,383 페이지로 커진 것과 일치합니다.

## 계획 시간이 늘어난 이유

1·5·6번의 계획 시간이 직렬·병렬 모두 약 0.9 ms에서 약 2.3 ms로 늘었습니다. 같은 데이터를 별도 임시 DB에 적재해 원인 후보를 확인했습니다(중앙값 12회, ms).

| 실험 | 계획 시간 |
|---|---|
| 정규화 쿼리 1 | 0.919 |
| 반정규화 쿼리 1 | 2.314 |
| 반정규화 쿼리 1, ISBN `EXCLUDE`(GiST) 제약을 지운 뒤 | 2.339 |
| 반정규화 분류 집계 쿼리, `(book_id, book_no)` 두 컬럼 조인 | 2.328 |
| 같은 쿼리, `book_id` 한 컬럼만 조인(비교용, 결과 의미는 다름) | 1.391 |
| 같은 쿼리, `(book_id, book_no)`에 확장 통계(`CREATE STATISTICS … dependencies, ndistinct`)를 만든 뒤 | 0.392 |

- **GiST 인덱스는 원인이 아닙니다.** 제약을 지워도 계획 시간이 같습니다.
- **두 컬럼 복합 조인 조건이 원인과 관련 있습니다.** 한 컬럼만 조인하면 2.33 → 1.39 ms로 줄고, 두 컬럼에 확장 통계를 만들면 0.39 ms까지 내려갑니다.
- 확장 통계를 만들었을 때 왜 이만큼 내려가는지, 실행 플랜이 바뀌는지는 확인하지 못했습니다. 이 통계는 이번 정식 측정에는 적용하지 않았으므로 문서의 수치에는 영향이 없습니다.
- 계획 시간이 늘어난 쿼리는 대출↔보유도서 조인이 남아 있는 1·5·6번이고, 조인이 없어진 3번은 직렬 0.402 → 0.169 ms로 줄었습니다. 나머지 2·4·7·8번은 거의 같습니다. 실행 시간이 12~84 ms인 쿼리들에서는 계획 시간 +1.4 ms의 비중이 쿼리마다 다릅니다. 1·6번에서는 실행 시간 단축에 비해 작지만, 11 ms대인 5번에서는 큽니다.
- 플래너 메모리는 병렬 계획이 직렬보다 더 씁니다(합 직렬 352 → 287 kB, 병렬 409 → 352 kB). 직렬에서 전/후 모두 더 작은 것은 병렬 플랜 후보를 만드는 비용이 빠지기 때문으로 보입니다(추정).

## 해석할 때 주의할 점

- **반정규화 이득은 조인이 줄어든 쿼리 중 3·6번에만 있고, 읽는 데이터는 오히려 늘었습니다.** 8개 쿼리 모두 실행 버퍼가 11~24% 늘었습니다. 대출 테이블이 연체 이력 컬럼을 흡수해 14% 커졌고, 보유도서가 서지 정보를 사본마다 중복 저장해 2배 가까이 커졌기 때문입니다. 조인 제거 이득이 데이터 증가를 앞선 쿼리(3·6번)만 빨라졌습니다.
- **직렬과 병렬의 결론이 다른 지점은 1번뿐입니다.** 병렬에서는 -46%로 가장 큰 개선처럼 보이지만, 전/후가 다른 전략(직렬/병렬)을 고른 효과가 섞여 있습니다. 반정규화의 순수한 효과는 직렬 측정으로 읽는 것이 맞습니다.
- **2번은 조인이 같고 변동이 커서 방향을 단정하기 어렵습니다**(직렬 +7%, 병렬 +6%, 병렬 2차 +22%, 모두 범위 겹침). 플랜은 같고(Hash Join + HashAggregate) 대출 테이블이 14% 커진 만큼 약간 느린 쪽으로 읽힙니다.
- **4번은 일관되게 느려졌습니다**(직렬 +12%, 직렬 2차 +13%, 병렬 +16%, 병렬 2차 +13%). 대출 테이블을 전체 읽고 필터하는 쿼리라 실행 버퍼 증가(+11~12%)가 시간에 가장 그대로 반영된 것으로 보입니다(추정).
- **메모리는 `work_mem`(4MB) 안에서 모두 해결되었고 디스크를 쓰지 않았습니다.** 가장 큰 단일 노드는 2번의 HashAggregate 2,193 kB입니다. 1번은 후에 Hash가 1,303 kB로 커졌는데, 해시 테이블에 올라가는 보유도서 행이 서지 정보까지 포함해 넓어졌기 때문입니다(행 폭 17 → 62바이트). 3번은 해시 조인이 없어져 실행 노드 메모리가 296 → 24 kB로 줄었습니다.
- **플래너 메모리·계획 버퍼는 줄었지만 계획 시간은 늘었습니다.** 두 지표는 같이 움직이지 않습니다. 계획 버퍼는 카탈로그 조회량, 계획 시간은 CPU 시간이라 복합 키 조인의 추정 계산 비용이 후자에만 반영된 것으로 보입니다(추정).
- **저장 공간은 거의 같습니다**(29.3 → 28.5 MB). 조인을 없애는 대가로 일부 테이블이 커지지만, 사라지는 테이블과 인덱스로 상쇄됩니다.
- **쓰기 비용은 이 문서에 포함되어 있지 않습니다.** 반정규화 쪽에는 사본 등록·서지 수정 트리거와 ISBN 검증이 있어 INSERT/UPDATE가 더 비쌉니다. 읽기 이득을 평가할 때는 이 쓰기 비용도 함께 측정해야 합니다.
- **데이터는 합성 샘플이고 측정은 한 세션입니다.** 모든 쿼리의 데이터가 캐시에 올라와 있어 디스크 읽기 비용이 반영되지 않았습니다. 절대값보다 버퍼·메모리·조인 수 같은 결정적인 지표의 방향을 근거로 삼는 것이 안전합니다.
