# 영화관 정보시스템 쿼리 응답시간·리소스 비교 (반정규화 전/후, 대량 샘플)

원본 로그: [`cinema/results_bulk_interleaved_parallel0/`](results_bulk_interleaved_parallel0)(직렬), [`cinema/results_bulk_interleaved_parallel2/`](results_bulk_interleaved_parallel2)(병렬). 폴더마다 `cinema_before_NN.log`·`cinema_after_NN.log`(자원 측정), `cinema_before_NN_time.log`·`cinema_after_NN_time.log`(시간 측정), `cinema_*_meta.txt`가 있습니다. 표의 수치는 이 로그에서 뽑았고, 로그에 없는 값은 따로 적었습니다.

[`EXECUTION_TIME_COMPARISON.md`](EXECUTION_TIME_COMPARISON.md)(기본 샘플, 쿼리당 10회)와는 데이터 크기와 측정 방법이 달라서 수치를 직접 비교하지 않습니다.

## 결론

- 9개 쿼리의 실행 시간 합은 직렬에서 +2.4%, 병렬에서 +0.5%로 후가 약간 느리거나 비슷합니다. 조인은 13개에서 9개로 줄었지만 예매 테이블이 커져서 읽는 양이 늘었고, 시간은 3·6번에서 늘어난 양(27.0 ms)이 4·5·8번에서 줄어든 양(7.7 ms)보다 컸습니다.
- 직렬에서는 3번(+7.7%)·6번(+4.2%)이 느려지고 4번(-3.9%)이 빨라졌습니다. 5번(-2.8%)과 8번(-2.4%)도 줄었지만 3% 안쪽이고, 5번은 전/후 사분위 범위가 겹칩니다. 빨라진 4·5·8번은 모두 `tbl_thtr_m1` 조인이 빠진 쿼리입니다(9번도 빠졌지만 차이가 없었습니다). 3·6번은 조인이 줄지 않았고 예매 테이블을 읽는 양만 늘었습니다. 줄어든 시간은 4번 2.5 ms, 5번 4.4 ms, 8번 0.8 ms입니다.
- 병렬에서는 3번 +3.5%(범위 분리), 4번 -4.4%(범위 분리)이고, 6번(+2.6%)·5번(-2.6%)·8번(-0.9%)은 3% 안쪽입니다. 병렬 플랜인 3·6번은 직렬보다 변화폭이 작습니다.
- 7번·9번은 직렬·병렬 모두 변화가 1.5% 안쪽이라 차이로 보지 않았습니다. 1번(+4.6%, 병렬 +4.2%)과 2번(+4.9%, 병렬 +6.4%)은 실행 시간이 1.3~2.6 ms인 쿼리라 차이가 0.06~0.11 ms입니다. 원인은 확인하지 않았습니다.
- 시간은 노드별 타이머와 버퍼·메모리 집계를 끈 `EXPLAIN (ANALYZE, TIMING OFF, ...)`로 따로 쟀습니다. 모든 계측 옵션을 켠 실행에서는 합이 988.2 → 990.7 ms(+0.3%)로 나오고 2번이 +35% 느려 보입니다. 이 차이는 "결과 > 계측 방식에 따른 시간 차이"에 정리했습니다.
- 데이터는 합성이고 Docker 안의 한 호스트에서 측정했으므로 운영 성능을 예측하는 근거로 쓰기는 어렵습니다.

## 측정 기준

| 항목 | 내용 |
|---|---|
| 실행 환경 | 실제 컨테이너 `db-optimization-postgres`, PostgreSQL 17.10 (aarch64), `shared_buffers`=16384 페이지(128MB), `work_mem`=4MB, `jit`=on(로그에 JIT 항목 없음), TimeZone=UTC, `max_parallel_workers_per_gather` 직렬 0 / 병렬 2 |
| DB | `cinema_normalized_bench`(정규화), `cinema_denormalized_bench`(반정규화) 두 개를 따로 만들어 둠. 같은 인스턴스라 `shared_buffers`를 함께 씀. 실제 `cinema` DB는 건드리지 않음 |
| 전 / 후 스키마 | 전: `cinema/postgresql/` (룩업 테이블 포함 정규화, 14개 테이블). 후: `cinema/postgresql_denormalization/` (v2.1.1, 11개 테이블). 측정은 v2.1.0 → v2.1.1 용어 변경 전 파일로 했고, 변경은 주석·메시지·별칭뿐이라 실행 계획은 같음 |
| 통계 상태 | 적재 직후 `default_statistics_target = 2000`으로 `VACUUM (ANALYZE)`. 표본(300 × 2000 = 60만 행)이 가장 큰 테이블(예매 31.5만 행)보다 커서 전체 행을 읽으므로 같은 데이터에서는 같은 통계가 나옴. 전/후 모두 모든 테이블이 분석된 상태이며 `cinema_*_meta.txt`에 기록 |
| 데이터 | 기본 샘플 + 대량 샘플(`postgresql_insert_data_bulk.sql`, `insert_data_bulk.sql`). 전/후 동일: 영화 310, 상영 14,628, 좌석 7,000, 회원 20,030, 예매 315,022, 충전 60,040, 찜 59,732. 값은 md5 해시로 정하고 날짜는 `CURRENT_DATE` 기준이라 같은 날에는 항상 같은 데이터. 좌석은 지정하지 않은 예매. 반정규화는 적재 중 사용자 트리거를 끄고 적재 직후 규칙(총 좌석 수와 Y 상태 좌석 수, 계획 좌석 수·이용 가능 좌석 수, 예매 수 ≤ 이용 가능 좌석 수 등)을 SQL로 확인한 뒤 다시 켬 |
| 쿼리 | `cinema/postgresql/postgresql_information_system.sql`(전)과 `cinema/postgresql_denormalization/information_system.sql`(후)의 1~9번. 전체 줄 주석을 제거하고 `;` 단위로 분리해 그대로 실행 |
| 자원 측정 | `EXPLAIN (ANALYZE, BUFFERS, MEMORY, WAL, SETTINGS, SUMMARY)`를 쿼리마다 전/후 DB에 워밍업 3회(버림) 후 3회. 버퍼·메모리·플랜·결과 행수를 읽는 용도이고 `cinema_*_NN.log`에 저장 |
| 시간 측정 | `EXPLAIN (ANALYZE, TIMING OFF, BUFFERS OFF, MEMORY OFF, SUMMARY ON)`을 쿼리마다 전/후 DB에 워밍업 3회(버림) 후 30회. 실행 시간과 계획 시간을 읽는 용도이고 `cinema_*_NN_time.log`에 저장 |
| 실행 순서 | 두 측정 모두 한 회에서 홀수 회는 정규화 → 반정규화, 짝수 회는 반정규화 → 정규화 순서로 번갈아 실행. 쿼리마다 자원 측정 뒤에 시간 측정. 캐시 초기화는 하지 않음(전 구간 버퍼 hit) |
| 플랜 확인 | 쿼리·DB마다 자원 측정 3회와 시간 측정 30회의 플랜 노드(종류, 순서, 대상 테이블·인덱스)가 모두 같은 한 가지였음. 7번은 양쪽 모두 `Heap Fetches: 0` |
| 시간 의존 쿼리 | "이번 달"은 `CURRENT_DATE`(로그의 `current_date=2026-11-10`), 8·9번은 현재 시각 이후 상영만 대상이라 결과 행수가 날짜·시각에 따라 달라짐. 직렬 측정 시작 2026-11-11 00:09, 병렬 2026-11-11 00:11 (KST). 8·9번 결과는 전/후 모두 5,490행 |
| 실행 명령 | `sh cinema/estimation_response_time_and_resource.sh setup` 후 `PARALLEL=0 ... measure`(직렬), `PARALLEL=2 ... measure`(병렬) |

## 집계 기준

| 지표 | 로그에서 읽는 값 | 집계 |
|---|---|---|
| 실행 시간 | 시간 로그의 `Execution Time` | 30회의 중앙값을 대표값으로 사용. 사분위 범위·최소·최대·변동계수(CV)는 보조 |
| 계획 시간 | 시간 로그의 `Planning Time` | 30회의 중앙값 |
| 실행 버퍼 | 자원 로그 플랜 최상위 노드의 `Buffers: shared hit`+`read` (병렬 워커 포함, `temp`는 제외). `read`·`dirtied`·`written`은 별도 확인 | 3회 중앙값 (쿼리·DB마다 3회가 모두 같은 값) |
| 계획 버퍼 | 자원 로그 `Planning:` 블록의 `Buffers: shared hit` | 3회 중앙값 |
| 플래너 메모리 | 자원 로그의 `Memory: used=…kB allocated=…kB` | 3회 중앙값 |
| 실행 노드 메모리 | 자원 로그 각 노드의 `Sort Method … Memory`, `Memory Usage`(Hash, HashAggregate, Memoize) | 노드별 값을 합산(근사치이며 동시 점유량이 아님). 디스크로 내려간 정렬(`Disk:`)은 포함하지 않음 |
| 노드 수 / 조인 수 | 자원 로그 `(cost=…)` 줄 수 / `Hash (Left·Right) Join`, `Nested Loop`, `Merge Join` 노드 수 | 첫 실행 기준 |
| 결과 행수 | 최상위 노드의 `actual … rows=` | 전/후 동일해야 비교 대상으로 인정 |
| 변화율 | (후 − 전) ÷ 전 | 합계 행은 쿼리별 중앙값의 합 |
| 판정 | 전/후 30회의 사분위 범위(1~3사분위)가 겹치면 "겹침". 변화가 3% 안쪽이면 범위가 겹치지 않아도 "3% 이내"로 두고 차이로 보지 않음. 버퍼·메모리·조인 수는 반복해도 같으므로 값 그대로 비교 | |

중앙값을 쓰는 이유는 한 번씩 튀는 값 때문입니다. 직렬에서 1번 후의 최대 9.75 ms는 중앙값 2.575 ms의 세 배를 넘고(CV 47%), 7번 전의 최대 11.99 ms도 중앙값 3.277 ms와 크게 다릅니다(CV 44%). 두 쿼리는 사분위 범위가 좁아서 중앙값은 이 값들에 영향을 받지 않았습니다.

### 계측 방식에 따른 시간 차이 (직렬)

같은 쿼리를 EXPLAIN 옵션만 달리해 잰 중앙값입니다. 앞의 두 열은 이번 로그에서, 세 번째 열은 같은 두 DB에서 따로 돌린 결과(로그 밖 값, 쿼리·방식마다 전/후 30회 번갈아)입니다.

| 5 | 202.175 → 190.986 (-5.5%) | 157.853 → 153.456 (-2.8%) | 155.691 → 150.113 (-3.6%) |

- 모든 계측 옵션을 켜면 시간이 크게 늘어납니다. 합으로 815.8 → 988.2 ms(전), 835.6 → 990.7 ms(후)입니다. 쿼리마다 늘어난 양(전 / 후)은 4번이 39.2 / 32.2 ms, 5번이 44.3 / 37.5 ms, 8번이 24.3 / 22.8 ms입니다. 조인이 빠진 쿼리에서 후 쪽이 덜 늘어나서 전체 옵션으로 재면 4번이 -9.2%로, TIMING OFF의 -3.9%보다 크게 빨라 보입니다. 다만 조인이 없는 3번도 10.9 / 7.4 ms로 차이가 있어서, 이 차이가 노드 수 때문인지는 확인하지 않았습니다.
- TIMING OFF 값과 `\timing` 값은 합 기준 +2.4%, +2.2%로 비슷하고, 3·4·5·6번의 방향도 같습니다. 8번은 `\timing`에서 -1.9%로 TIMING OFF(-2.4%)와 크기가 조금 다릅니다.
- 2번의 차이(+35%)는 `MEMORY` 옵션 때문으로 보입니다. 2번(`SELECT name, savings FROM tbl_mebr_m1`)은 전/후 플랜이 같고 버퍼(427)와 결과 행수(20,030)도 같습니다. 옵션만 바꿔서 같은 쿼리를 두 DB에 번갈아 30회씩 실행한 결과가 아래 표입니다(로그 밖 값, 앞서 측정).

| `EXPLAIN` 옵션 | 정규화 → 반정규화 중앙값 |
|---|---|
| `ANALYZE` | 2.094 → 2.188 ms (+4.5%) |
| `ANALYZE, BUFFERS` | 2.196 → 2.268 ms (+3.3%) |
| `ANALYZE, MEMORY` | 2.091 → 2.627 ms (+25.6%) |
| `ANALYZE, BUFFERS, MEMORY, WAL, SETTINGS, SUMMARY` | 2.240 → 3.042 ms (+35.8%) |

`MEMORY` 없이는 +3~5%이고, 켜면 반정규화 쪽만 느려집니다. 이유는 알아내지 못했습니다. 이번 시간 측정(`MEMORY OFF`)에서도 2번은 +4.9%(약 0.06 ms)가 남았습니다.

## 해석할 때 주의할 점

- 3·6번은 예매 테이블을 읽는 쿼리입니다. 예매 테이블은 컬럼이 9개에서 11개로 늘어 힙이 28 MB에서 33 MB로(페이지 3,580 → 4,201), 인덱스가 6.9 MB에서 10.2 MB로 커졌습니다(로그 밖 값, 측정 뒤 DB에서 확인). 이를 읽는 3번(3,583 → 4,204 버퍼)과 6번(3,586 → 4,207)은 읽는 양이 늘었고 시간도 직렬에서 +7.7%, +4.2% 늘었습니다. 병렬 플랜에서는 +3.5%, +2.6%입니다. 읽는 양이 시간 증가의 원인인지는 따로 검증하지 않았고, 두 쿼리 모두 읽는 양과 시간이 같은 방향으로 움직였다는 점까지만 확인했습니다.
- 4·5·8·9번은 버퍼가 약 17% 늘었는데도 시간은 줄거나 비슷합니다. 4·5·8번에서 줄어든 시간은 2.5 / 4.4 / 0.8 ms이고(5·8번은 3% 이내), `tbl_thtr_m1` 조인 노드가 빠진 것과 방향이 맞습니다. 다만 노드별 시간은 TIMING 옵션을 켠 자원 로그에서만 볼 수 있고 그 값에는 계측 비용이 섞여 있어서, 조인 노드 하나가 몇 ms를 차지하는지는 이번 로그로 확정하지 않았습니다. 9번은 조인이 줄었어도 +0.6%라 차이로 보지 않았습니다.
- 4·5·6번은 정렬이 `work_mem`(4MB)을 넘어 디스크를 쓰고(5번 `external merge Disk: 5424kB`), 전/후 같은 양이라 비교에는 같은 비용이 양쪽에 들어갑니다.
- 계획 시간은 조인이 줄어든 4·5·8·9번에서 거의 같고(-0.042 ~ +0.012 ms), 3·6번은 0.389 → 0.469, 0.448 → 0.520 ms로 늘었습니다. 예매 테이블 인덱스가 하나 늘어서일 수 있지만 확인하지 않았습니다.
- 저장 공간은 `meta`의 `size_total`로 53 → 61 MB, 예매 테이블(`size_bytk`)은 35 → 43 MB로 늘었습니다. 두 DB의 `pg_total_relation_size` 합을 따로 구한 값은 52.55 → 61.34 MiB입니다(로그 밖 값, 측정 뒤 DB에서 확인). 예매 테이블의 인덱스가 3.3 MB(3,304 kB) 늘어난 것은 이번 버전에서 추가한 `UNIQUE (scrn_id, seatcode)` 때문인데, 이번 샘플은 좌석을 지정하지 않은 예매라 이 인덱스의 키가 전부 NULL입니다.
- 6번은 비교 기준이 바뀌었습니다. `buydate`(결제 완료 시각)가 아니라 `reserved_at`(예약 시도 시각)을 사용하고, 결과는 같았습니다(28행).
- 처음에는 DB 하나에 정규화 스키마를 적재해 측정하고, 지운 뒤 반정규화 스키마를 적재해 측정했습니다. 그 방식에서는 7번이 나중에 측정한 쪽에서만 다른 플랜(힙을 다시 읽는 Index Only Scan, `Heap Fetches` 6121)을 타서 15~20% 느리게 나왔습니다. 적재 직후 가시성 맵이 비어 있었던 것으로 보입니다. 그때 로그는 지금 없어서 다시 확인할 수 없습니다. 지금은 두 DB를 미리 `VACUUM`해 두고 번갈아 측정하며, 7번은 양쪽이 같은 플랜(`Heap Fetches` 0)이고 변화는 +1.3%입니다.

## 한계

- 읽기 쿼리만 측정했습니다. 반정규화의 트리거 4개가 쓰기에 주는 영향은 측정하지 않았고, 대량 적재도 사용자 트리거를 끄고 했습니다.
- 한 번의 실험입니다. 사분위 범위와 CV는 이 실험 안의 변동만 보여 주고, 호스트 상태가 달라질 때 생기는 실험 간 차이는 반영하지 않습니다. 직렬과 병렬은 같은 DB를 연달아 측정한 것이라 독립된 반복이 아니므로, 절대값보다 방향이 같은지를 근거로 삼는 것이 안전합니다. 같은 DB에서 앞서 따로 돌린 TIMING OFF 측정(로그 밖)에서도 3·6번이 느리고 4·5·8번이 빠른 방향은 같았습니다.
- 변화가 3% 안쪽인 쿼리(직렬 5·7·8·9번, 병렬 5·6·7·8·9번)와 절대 차이가 0.1 ms 안팎인 1·2번은 이번 측정만으로 방향을 단정하기 어렵습니다. 1번은 `\timing`에서 -2.0%로 TIMING OFF(+4.6%)와 방향이 달랐습니다.
- 시간은 서버가 보고하는 `Execution Time`이고 결과 전송 시간은 들어 있지 않습니다. 결과 행이 많은 쿼리(8·9번 5,490행)에서는 클라이언트가 받는 시간이 더 걸릴 수 있습니다. `\timing` 값에는 계획 시간과 전송 시간이 포함되고, 1번을 뺀 나머지 쿼리는 TIMING OFF와 방향이 같았습니다.
- 자원 측정은 쿼리·DB마다 3회입니다. 버퍼와 플랜은 3회가 모두 같았지만 플래너 메모리와 노드 메모리는 3회 중앙값입니다. 노드별 실행 시간은 계측 비용이 섞여 있어 원인 분석에 쓰지 않았습니다.
- `MEMORY` 옵션이 반정규화 쪽 2번만 느리게 만드는 이유와, TIMING OFF에서도 남은 2번·1번의 작은 차이의 원인은 확인하지 못했습니다.
- 두 DB가 `shared_buffers`를 함께 쓰고, 반정규화 예매 테이블(4,201 페이지)은 `shared_buffers`의 1/4(4,096 페이지)보다 약간 큽니다. 이보다 큰 테이블의 순차 스캔은 작은 링 버퍼를 쓰는데, 이번 로그에서는 `shared read`가 없어 영향이 보이지 않았습니다. `shared_buffers`를 바꿔 다시 측정하지는 않았습니다.
- 데이터는 합성입니다. 예매 좌석이 지정되지 않은 샘플이고 한 호스트의 Docker 컨테이너에서 측정했습니다.
